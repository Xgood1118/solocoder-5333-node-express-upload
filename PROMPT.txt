用 Node.js + Express 写一个文件上传服务（分片上传 + 秒传 + 断点续传）。

基础上传：
- 单文件上传
- 多文件上传
- 文件类型校验（按扩展名和 MIME）
- 文件大小限制（默认 100MB，可配置）

分片上传（核心）：
- 客户端把文件切成固定大小的块（默认 5MB）
- 客户端先调一个接口拿上传 ID 和分片信息
- 客户端按块上传（每个块单独请求）
- 服务端把分片临时存到磁盘
- 客户端全部上传完成后调合并接口
- 服务端按顺序合并分片到最终文件
- 合并完成后清理分片

秒传：
- 客户端先调 hash 计算接口（或者前端算好 hash 直接传）
- 服务端查 hash，如果文件已存在直接返回成功（不重复上传）
- hash 算法用 md5 或者 sha256（小文件 md5 够用，大文件用 sha256）

断点续传：
- 客户端传某个文件前先调"查询上传进度"接口
- 服务端返回这个上传 ID 已经上传了哪些分片
- 客户端只传缺失的分片
- 上传 ID 24 小时不活跃自动清理

上传限流：
- 单 IP 每秒最多上传多少 MB
- 单文件最多同时 N 个分片在传
- 限流超了返回 429

进度通知：
- 上传过程中通过 SSE 推送进度给前端
- 客户端订阅某个上传 ID 的进度事件
- 进度数据：已上传字节、总字节、当前分片、速度、剩余时间

文件管理：
- 已上传文件列表
- 删除文件
- 重命名
- 文件元数据（原始文件名、hash、大小、上传时间、上传者）
- 文件存储在本地文件系统（不用数据库）
- 提供 /files/:id 下载接口

至少 3 个文件：app.js（入口）、upload.js（上传逻辑）、storage.js（存储抽象）。依赖：express、multer（如果用，注意它自己处理 multipart）、或者用 busboy（更底层）。

实际使用里会有这些细节：用户上传同名文件不覆盖（生成唯一 ID）；分片乱序到达要正确合并（按分片索引）；分片缺失/重复要正确处理；用户取消上传时清理临时分片；磁盘空间不足返回明确错误（不写一半留在那里）；上传超大文件（10GB+）不能爆内存（流式处理）。



时间相关和配额。临时分片保留 24 小时，超期清理；超时判定为"upload_id 创建后 24 小时内没有 complete 请求"。月度流量配额每月 1 日 00:00 UTC 重置，重置前 24 小时给"剩余 10%"警告。月度配额用完后上传初始化直接返回 429，错误信息提示"下月 1 日重置"。并发分片数限制：单文件最多 5 个分片同时在传（防单用户占满带宽）。

数据一致性场景。删除文件时关联的缩略图（thumbnail_path 字段）、预览图（preview_path 字段）、秒传记录（hash_index 表）一起处理：缩略图和预览图物理删除，秒传记录引用计数 -1 归零才物理删除文件本身。同名文件 hash 冲突时（不同文件名相同内容），秒传命中直接返回已有 file_id，但要在 owner 维度加一条映射记录（不修改原文件的 owner）；原文件删除时引用计数减到 0 才真正清理。上传时如果用户改了文件再重新传（hash 变了但文件名相同），新文件独立存储，旧文件按 owner 看到自己的"两个同名不同 hash"文件，删除时互不影响。

实际部署里还会涉及这些点：文件 hash 计算（大文件用流式 hash）。分片大小可配置（默认 5MB，用户可改）。分片上传并发数限制（同一上传最多 N 个分片在传）。上传进度 SSE 推送频率（默认 1 秒）。上传完成通知（webhook）。上传限流（按 IP / 按用户）。文件去重（hash 命中直接返回）。文件预览（图片缩略图）。文件 ACL（哪些用户能上传）。

补段使用场景：用户用这个上传服务做文件存储。客户端上传大文件（10GB）到服务端。客户端先调 GET /upload/init 拿 upload_id 和分片大小，客户端按 5MB 切分文件，依次上传分片（POST /upload/chunk?upload_id=xxx&index=N），最后调 POST /upload/complete?upload_id=xxx 合并分片。

核心功能：分片上传（默认 5MB/片），秒传（客户端算文件 hash，服务端查 hash 命中直接返回成功），断点续传（客户端调 GET /upload/status?upload_id=xxx 查已上传分片，只传缺失的）。

文件管理：已上传文件列表、删除、重命名、文件元数据（原始文件名、hash、大小、上传时间、上传者）。文件存储在本地文件系统（不用数据库）。提供 /files/:id 下载接口。

限流：单 IP 每秒最多上传多少 MB。单文件最多 N 个分片并发。限流超了返回 429。进度推送：上传过程中通过 SSE 推送进度给前端。hash 计算：大文件用流式 hash（不全加载到内存）。

文件上传用 multer 库，存储策略分两种：小文件（< 10MB）存内存直接处理（生成缩略图、预览），大文件走磁盘临时文件。文件名用 UUID 重命名避免冲突，保留原始扩展名。MIME 类型校验：魔数（文件头字节）而不是扩展名。

分片上传：大文件分片（每片 5MB）并发上传，前端用 Web Worker 调度并发数（默认 3）。每片上传成功后服务端临时存储，前端全部上传完成发"合并"请求，服务端按顺序合并文件。断点续传：上传中断后下次可以从上次成功的分片继续，查询接口返回已上传的分片号列表。

安全防护：上传目录不可执行（disable script execution），Content-Type 严格白名单（图片只允许 png/jpg/webp/gif），文件大小限制（单文件 100MB），防 DoS 的限流（每 IP 每分钟 10 个文件）。
实际工作流里上传任务有完整状态机：上传从"待初始化"走到"已完成"中间要经过"分片上传中—合并中—已完成—已失败—已取消"几个状态；"合并中"阶段如果磁盘满了或者权限问题会回退到"已失败"并保留已上传的分片（方便续传）。状态迁移规则：手动取消（用户主动调 abort）走"已取消"清理所有分片；超时无活动 24 小时自动"已取消"；合并失败 3 次后"已失败"。

按角色上传权限不同。普通用户上传走严格 MIME 魔数校验（防止改后缀绕过），单文件最大 100MB，月度流量配额 5GB。VIP 用户跳过 MIME 校验（信任度高）但仍限制单文件 500MB 和月度 50GB，配额用完后降级到普通用户策略。审计员账号只读不写，能查所有上传记录和秒传命中日志。匿名访问（未登录）只能调上传初始化接口不能真正上传分片，初始化直接返回 401。
